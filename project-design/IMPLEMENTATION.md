本文把已确认范围拆成可以实现、测试和验收的模块。表结构与 API 是初始契约建议，工程初始化时落成迁移和 OpenAPI 文档。

## 1. 产品仓库组织

建议为产品建立独立仓库，当前 Go 学习项目继续作为学习资料。

```text
ai-code-notes/
  apps/
    web/                 Next.js 网页
    desktop/             Electron 主进程与渲染端
    mobile/              React Native
    miniapp/             uni-app
  services/
    api/                 Go / Gin 业务服务
    ai/                  Python，包含 FastAPI 与 Celery Worker
  packages/
    contracts/           生成的客户端接口类型
    markdown/            确实被多个客户端使用的内容处理逻辑
    editor/              可复用的 React 编辑器与受控 WebView 编辑界面
  deploy/
    compose/             开发和服务器部署配置
    proxy/               反向代理配置
  docs/
    CONTEXT.md
    architecture.md
    api/
  evals/                 AI 评测样本与结果
```

Go 初期使用一个模块化业务服务，按 auth、projects、sources、topics、documents、jobs、sharing 分包。Python API 和 worker 从同一套业务代码构建，以不同命令启动。实际出现共享需求时再创建 packages 中的目录。

Electron 的本地目录能力由主进程提供，渲染层只调用明确的受限接口。网页与桌面可以共享 React 编辑组件，uni-app 通过接口和内容格式复用能力。

## 2. 数据模型

主键建议统一使用 UUID；时间统一记录 UTC。核心修改使用数据库事务，业务约束优先由唯一键、外键和检查约束保证。

| 逻辑表 | 核心内容与约束 |
| --- | --- |
| users | 用户身份、密码哈希、账号状态；登录标识唯一 |
| auth_identities | 外部平台与平台用户标识的账号绑定，组合唯一 |
| sessions | 设备、刷新凭证哈希、有效期、撤销状态和轮换关系 |
| knowledge_spaces | 个人空间与拥有者，初期每人一个默认空间 |
| projects | 所属空间、名称、介绍、归档状态 |
| source_roots | 项目的来源目录标识、同步设备、纳入与排除规则；不以用户绝对路径作为云端权限依据 |
| source_files | 来源目录、相对路径、语言、当前快照、删除标记；目录与有效相对路径唯一 |
| source_snapshots | 不可变内容、哈希、对象存储标识、版本与采集时间 |
| source_fragments | 所属快照、片段标识、行号、代码符号、注释与上下文 |
| topics | 所属项目、主题说明、目录大纲与状态 |
| topic_sources | 主题与来源文件或片段的关系，支持多个文件共同构成主题 |
| documents | 所属主题、当前修订、自动更新设置与新鲜度状态 |
| document_revisions | 不可变 Markdown、父修订、作者或任务、内容哈希、创建时间 |
| generation_states | 文档已采纳的生成基线、区块对应关系和来源快照集合 |
| update_conflicts | 冲突区块的基线、当前内容、候选内容、来源及处理结果 |
| evidence_items / citations | 外部参考或代码证据，以及文档修订与证据的关联 |
| resource_grants | 资源、被授权用户、阅读或编辑权限及授予者 |
| jobs / job_events | 任务的业务状态、执行尝试、输入快照、进度事件和终态 |
| outbox_events | 与业务事务一起写入的待投递事件、投递状态和重试信息 |
| conversations / messages | 知识问答、消息、引用、用量和会话可访问范围 |
| ai_usage | 模型、用途、任务、Token、耗时、计价版本与估算费用 |
| sync_devices / sync_cursors | 来源同步和文档同步的设备标识、游标与恢复信息 |
| audit_logs | 授权变更、内容删除、版本恢复等重要操作记录 |

resource_grants 可以分别关联 project_id、topic_id 或 document_id，要求恰好一种目标非空，并建立真实外键。不要仅保存任意“类型 + 字符串 ID”而失去数据库一致性检查。

owner、editor、viewer 是资源级权限。项目授权可以覆盖其中主题和文档；文档单独授权不扩大为整个项目权限。公开匿名分享暂不作为注册用户协作的默认方式。

空间隔离不能只靠请求里传入的 space_id。服务端从登录身份及授权关系确定可访问范围，对存储下载、历史版本、问答检索和后台任务一并检查。

必要索引包括外键、项目文件路径、文档当前修订、资源授权查询、任务状态与更新时间、事件的任务编号及序号。向量维度在选定模型后创建，切换模型时对索引版本进行迁移或重建，不混用不同向量空间。

## 3. 身份认证和协作

- 基础注册登录与密码重置使用同一账号体系。密码用成熟密码哈希方案保存，禁止明文或直接 SHA-256。
- JWT 用于短期访问。刷新凭证绑定可撤销会话，只保存其哈希，刷新时轮换并处理旧凭证重复使用。
- 网页优先使用安全的 HttpOnly Cookie，配合 SameSite、CSRF 和正确的跨域规则。
- 桌面和移动端使用系统安全存储保存长期凭证，访问凭证尽量保存在内存。小程序遵循平台登录和本地存储约束，后端支持撤销会话。
- 页面权限提示与服务端权限校验同时存在，服务端判断是最终依据。
- 共享目标用户必须是可明确识别的账号；权限调整后新请求及后台任务重新校验。拥有者可以移除协作者。
- 共享成果中的代码片段属于共享内容，查看完整来源文件仍需来源权限。授权界面说明共享范围。
- 每次人工保存携带 base_revision_id。版本过期返回 409 与当前版本信息，客户端展示差异或提交冲突处理结果。

账户中心支持查看并退出指定设备。一般用户管理的是自己的空间、会话和分享；运维管理权限单独控制。

## 4. 来源同步与 Markdown 文件同步

来源目录和成果输出目录各自绑定，不把生成结果再次当成待整理来源。

### 4.1 来源同步

1. Electron 记录用户选择的目录和纳入规则，只访问授予权限的范围。
2. 扫描代码及注释，计算内容哈希；忽略依赖、构建产物、版本控制元数据、密钥文件及生成文档目录。
3. 连续保存合并成批次，提交新增、修改、删除和可确认的重命名。
4. Go 校验路径、类型、大小和授权，保存不可变来源快照。
5. 解析过程关联注释、函数、类型和上下文，保留快照标识与行号。
6. 根据 topic_sources 查出受影响主题，创建可去重的整理任务。
7. 重新连接时对账快照清单和同步游标，补上未上传变化。

初始语言范围建议 Go、Python、JavaScript、TypeScript。TSX / JSX 及 Vue 单文件组件按实际资料接入对应解析器。不支持的类型明确显示状态，不能伪装成成功解析。

符号链接和路径跳转不能越过授权目录。代码按文本与语法结构分析，导入过程不执行仓库脚本。

文件删除创建来源墓碑；已有文档与历史引用保留，并标明来源已删除。用户明确永久删除资料时，按保留规则清理数据，同时指出受影响的引用。

### 4.2 独立 Markdown 文件

Electron 可将主题文档同步到用户选择的成果目录，使用户能用自己的编辑器直接修改 .md 文件。

本地同步清单记录文档 ID、服务端基线修订、上次同步内容哈希和附件映射。该清单属于客户端状态，不要求用户在正文里维护内部 ID。

- 本地人工改动作为文档编辑提交，携带基线版本。
- 收到服务端新版本时，先检查本地文件是否仍等于上次同步内容，再写入。
- 本地已有未提交修改时，按三方内容比较处理；有冲突保留本地内容并展示待处理项。
- 程序写入完成后更新同步清单，文件监听器识别此次写入，避免反复上传同一版本。
- 写文件采用临时文件与安全替换方式，失败时保留现有文件并提供重试状态。

文件导入、代码来源同步、生成文档同步是不同事件类型。编辑知识文档不会自动回写来源代码的注释。

## 5. AI 任务可靠性

队列负责调度，Go 数据库中的 jobs 才是前端看到的任务事实来源。

建议状态：queued、running、retry_wait、cancel_requested、cancelled、succeeded、failed。文档“存在冲突”或“含待核实内容”作为独立结果标记；任务处理完成不代表所有人工冲突都已解决。

一次任务的必要输入包括 job_id、发起身份、主题、来源快照清单、文档基线、授权范围、提示词版本、模型配置和预算。

### 5.1 投递与恢复

1. Go 在同一事务内创建业务任务与 outbox 记录。
2. 投递器把任务标识提交给内部 Python API，由其入 Celery 队列。
3. worker 执行前向 Go 领取当前执行尝试及租约。重复消息遇到有效执行租约时跳过。
4. 租约通过心跳续期；过期任务经过检查重新排队。回调携带执行尝试标识，过期 worker 的回调不能覆盖新尝试。
5. Python 检查点保存 AI 执行状态；Go 保存业务任务和文档状态，两者使用不同数据库权限。
6. 完成后回传候选稿及证据，Go 校验、合并并以事务保存修订、任务结果与事件。
7. 进程重启后扫描未完成任务并恢复投递，不能只依赖 Redis 中是否还有消息。

任务按至少一次投递设计，发布结果必须幂等。不要把一次 HTTP 成功提交理解为任务已经可靠完成。

同一主题的新来源变化可以合并待执行任务，或让旧任务的候选结果标记为过期。即使旧任务较晚返回，也必须经过最新来源和文档版本检查。

### 5.2 重试与取消

网络短暂失败、限流等采用有上限的退避重试；输入错误、无权限和不可恢复解析失败直接报告原因。模型请求发生重试可能产生额外费用，记录执行尝试和调用用量。

用户取消后先持久化取消请求。未开始的任务可以撤销；运行中的任务在步骤边界及支持取消的网络操作处停止。取消与完成竞争时，由 Go 的状态事务决定哪个终态有效。

模型调用、外部抓取和总工作流都有超时、最大步骤及预算。任何一个 Agent 的重试都不能绕过整项任务的预算。

Celery 调度投递与 AI 步骤重试需要各自明确责任，避免两层无限叠加。检查点恢复时复用已验证的工具结果和证据，减少重复请求。

## 6. API 契约草案

所有对外业务路由位于 /api/v1。列表采用明确的分页规则，错误统一返回 code、message、request_id，按场景附带字段错误或当前版本信息。

| 接口组 | 主要路由与行为 |
| --- | --- |
| 身份 | POST /auth/register、/auth/login、/auth/refresh、/auth/logout；GET /me |
| 会话 | GET /sessions；DELETE /sessions/{id} |
| 项目 | GET/POST /projects；GET/PATCH/DELETE /projects/{id} |
| 来源目录 | POST /projects/{id}/source-roots；GET/PATCH /source-roots/{id} |
| 来源批次 | POST /source-roots/{id}/batches；按客户端批次 ID 去重 |
| 文件与快照 | GET /source-files/{id}；GET /source-files/{id}/snapshots；GET /source-snapshots/{id} |
| 附件 | POST /uploads；POST /uploads/{id}/complete；下载前检查资源授权 |
| 主题 | GET/POST /projects/{id}/topics；GET/PATCH /topics/{id}；维护主题与来源关系 |
| 整理 | POST /topics/{id}/organization-jobs；立即返回 202、job_id 和查询地址 |
| 任务 | GET /jobs/{id}；POST /jobs/{id}/cancel；GET /jobs/{id}/events |
| 文档 | GET /documents/{id}；PUT /documents/{id}/content，要求 base_revision_id |
| 修订 | GET /documents/{id}/revisions；GET /documents/{id}/revisions/{revision_id} |
| 恢复 | POST /documents/{id}/restore，携带目标修订与当前基线，生成新修订 |
| 冲突 | GET /documents/{id}/conflicts；POST /conflicts/{id}/resolve，携带预期版本 |
| 授权 | GET/POST /documents/{id}/collaborators；PATCH/DELETE /documents/{id}/collaborators/{user_id}；项目和主题遵循同类规则 |
| 问答 | POST /conversations；POST /conversations/{id}/messages；查询回答、引用与状态 |
| 导出 | POST /documents/{id}/exports；返回导出结果或导出任务 |
| 用量 | GET /usage；按调用用途、模型与日期汇总 |
| 同步 | GET /sync/changes?cursor=...；只返回调用者可访问的变更 |

事件序号在单个任务内单调递增。支持 Last-Event-ID 或游标恢复；权限变化后不继续发送私有事件。Web/Electron 可用 SSE；移动和小程序选择平台支持的事件通道，并提供同等的任务状态查询。

Go 与 Python 的内部接口独立于对外 API，包含提交任务、领取与续期执行租约、检查取消状态、请求授权资料、提交事件和回传结果。使用服务身份及受限任务凭证，内部地址不公开给客户端。

AI 的结构化输出至少包含主题标识、大纲、Markdown 区块、来源引用、图表源码、待核实项和使用的来源快照。非法引用、丢失代码块或不符合结构的输出不能直接发布。

## 7. 版本合并的实现约定

“人工修改”和“AI 更新”都通过相同的文档版本入口写入。

普通编辑保存逻辑：验证权限，检查 base_revision_id，插入新修订，以旧版本作为条件更新 documents.current_revision_id。条件更新失败则返回冲突，整个事务回滚。

AI 更新需要额外维护生成基线，不把所有当前文档内容都当作 AI 的上一版输出。冲突区块的旧基线与新候选保持独立，处理冲突时才明确新的基线关系。

建议先对 Markdown 解析后的区块做定位与差异计算，再对局部文本使用成熟的合并能力。先做保守合并，无法可靠定位时提示冲突。区块重新排序或标题改名不应依赖单一行号判定。

引用使用来源快照与片段标识，并保存展示行号。当前本地文件已经变化时，先展示生成时的快照；只有确认仍能定位时才直接跳到当前文件的对应位置。

文档历史恢复、AI 更新和离线草稿上传都检查当前版本。禁止以“最后一个请求到达”为规则覆盖别人内容。

## 8. 业务与 AI 边界验证

必须保留的自动化检查：

- 用户 A 无法通过改资源 ID、下载地址、历史版本或检索参数访问用户 B 的私有资料。
- 被撤销权限的协作者不能继续保存、启动越权任务或收到新增私有事件。
- 重复同步批次、重复队列消息、重复回调不会多发文档修订。
- 任务执行期间来源和文档再次变化，旧结果无法覆盖新状态。
- 两人基于同一修订编辑并先后保存，后一次得到冲突，前一次内容保留。
- AI 与人工修改同一区块时进入冲突；互不冲突的人工内容保留。
- 本地 Markdown 有未同步修改时，远端新修订不会直接覆盖本地文件。
- 输出文件变化不会被误判为新的代码输入而形成生成循环。
- 进程、worker 或 Redis 重启后，未完成任务可恢复或明确失败。
- 四端的 Markdown 往返、代码块、Mermaid、引用与图片都通过共同样例。
- 外部资料抓取失败或证据不足时，输出明确状态，不编造已查到的来源。
- 恢复备份后，业务数据、文档修订、附件与引用保持可访问关系。

测试工具建议：Go 标准库 testing/httptest，Python pytest，前端按框架采用对应组件与端到端工具。测试围绕业务边界和失败路径，不为每个数据转发函数建立重复测试。

## 9. 本地开发与阿里云部署

开发环境通过 Docker Compose 启动 PostgreSQL、Redis、Go API、Python API/worker 和网页服务。需要断点或热更新时，应用进程可以在宿主机运行，数据服务仍由 Compose 管理。

建议配置项按服务最小范围分配：数据库连接、Redis 连接、业务签名密钥、服务间凭证、DeepSeek 密钥、对象存储凭证、公开地址和预算参数。密钥不写入镜像、客户端或版本库。

初期线上结构：

```text
公网 HTTPS
  -> 反向代理
      -> Next.js
      -> Go API

私有服务网络
  -> Python API / Celery Worker
  -> PostgreSQL
  -> Redis

持久化
  -> PostgreSQL 数据卷与备份
  -> Redis 持久化卷
  -> 阿里云 OSS 原始资料、附件与导出文件
```

对外只开放必要入口，数据库、Redis 和内部 AI API 使用私有网络。运行镜像以固定版本发布，数据库迁移作为明确的发布步骤。

Redis 同时承担队列和缓存时，初期启用持久化并采用避免队列被淘汰的内存策略；普通缓存设置过期和大小上限。出现容量压力再分离缓存和队列实例。任务恢复仍依赖数据库账本。

备份不仅要执行，还要定期在测试环境恢复。定义恢复点、可接受的停机时间和保留周期，在上线前实际演练。

构建发布流程覆盖 Go 测试、Python 测试、前端检查、镜像构建、迁移、健康检查和回退。部署回退要同时考虑数据库兼容性，不能只回退镜像。

桌面、移动和小程序分别完成目标平台构建与发布验证。iOS/macOS 签名、小程序账号与合法域名等按实际发布平台准备，不以网页测试结果代替原生端验证。

## 10. 最小可用的观测体系

统一 request_id、job_id、user_id、source_snapshot_id 和 document_revision_id 等关联信息。日志避免记录密码、访问凭证、完整私有代码和敏感请求体。

业务看任务队列长度、等待时间、完成耗时、失败与取消比例、冲突数量；AI 看 Token、模型调用耗时、重试、引用缺口和评测结果。

模型费用按调用时的计价配置估算，并保留原始用量；提供方账单是实际结算依据。自动更新按变更合并、哈希复用、主题范围和预算限额控制调用量。

LangGraph 检查点和调试记录可能包含私有资料，按业务数据的权限和保留策略处理，不默认上传到第三方追踪平台。

## 11. 分阶段开发与验收

| 阶段 | 实施内容 | 验收结果 |

## 13. 开工时的第一组任务

1. 创建独立产品仓库，迁入本设计资料，确定客户端目标平台及依赖版本。

5. 打通注册登录和跨端读取同一文档，验证用户之间的数据隔离。
6. 用固定样例验证四端富文本、Markdown、代码块和 Mermaid 往返。
7. 再接来源文件导入与首次 AI 整理，向量模型到检索阶段再决定。
